# block-main-push.sh: honest-naming as a blocking backstop, not demotion

> In the context of me2resh/apexyard#1086 step 3 — deciding what happens to `.claude/hooks/block-main-push.sh`'s commit-half now that #1090 gave pushes a git-native, ground-truth control (`.githooks/pre-push` + `_lib-protected-branches.sh`) — facing a proposal, informed by a Solution-Architect design pass and a Contrarian (Naqid) challenge, to demote it to advisory the same way #1090 treated the push side, I decided to **add the missing git-native commit-time control (`.githooks/pre-commit`), harden the shared protected-branch lib fail-closed, and honestly relabel `block-main-push.sh` as a blocking BACKSTOP rather than THE control — but keep it blocking, not demote it** — to achieve the honest-naming AgDR-0104 asked for without the net coverage loss a straight demotion would cause, accepting that `block-main-push.sh`'s own text-parsing residuals (AgDR-0113's catalogued #1081/#1083/#1084/#1085) stay open a while longer, deferred to a follow-up PR rather than fixed here.

## Context

`.claude/hooks/block-main-push.sh` has been the sole blocking control against direct commits/pushes to protected branches since apexyard#109. #1086 set out to replace its text-parsing with git's own ground truth: step 1 (#1087) installed `.githooks/` by default via `core.hooksPath`; step 2 (#1090, merged) gave `.githooks/pre-push` a git-native, stdin-ref-based check plus the shared `.claude/hooks/_lib-protected-branches.sh` resolution lib. Both landed clean — pushes now have a control that reads git's own resolved refs, immune by construction to every heredoc/decoy/quoting shape AgDR-0113 spent five review rounds cataloguing for the text-parsing approach.

Step 3 — what happens to `block-main-push.sh` now that a stronger push-side control exists — went through several rounds of scope revision on the issue itself, tracked in the issue's own comment thread:

1. The original ticket scope said `block-main-push.sh` "becomes an advisory."
2. A review round found that wording was a **net reduction in protection**: `block-main-push.sh` blocks *commits* too, and `.githooks/` had no `pre-commit` hook at all — demoting the only commit-time blocking control with nothing replacing it would leave protected-branch commits ungated.
3. A follow-up comment on the issue ("Decision recorded: AgDR-0114 — the commit gate moves to a pre-commit hook", 2026-07-31T06:32:30Z) proposed the fix: add `.githooks/pre-commit` as the new commit-time control, **and demote `block-main-push.sh`'s commit half to advisory once it lands** — mirroring #1090's push-side shape exactly.

That proposal's own file (`docs/agdr/AgDR-0114-commit-gate-moves-to-pre-commit-hook.md`) was never actually committed — verified against every branch, every PR (open and merged), and `origin/dev`'s current tree before writing this record, precisely so this AgDR doesn't collide with an artifact that already exists. There is none; `AgDR-0113` is still the highest committed record. This document is the actual, corrected decision for the same open question, occupying the same next-available slot the proposal announced but never filed.

**Why the proposal doesn't hold up.** A Solution-Architect design pass plus a Contrarian challenge on the "demote once pre-commit lands" plan surfaced two concrete, currently-live gaps that a straight demotion — even a correctly-sequenced one — does not close, because nothing else in the system covers them:

1. **`git push --no-verify` / `git commit --no-verify` skip git-native hooks by git's own design.** `.githooks/pre-push` and the new `.githooks/pre-commit` are both ordinary git hooks — `--no-verify` bypasses them, full stop, not a bug to fix. `block-main-push.sh` is different in kind: it is a Claude Code **PreToolUse** hook (wired in `.claude/settings.json`) that intercepts the `Bash` tool call **before the shell — and therefore before git, and therefore before `--no-verify`'s effect — ever runs**. It is the only layer in this system structurally immune to `--no-verify` for agent-driven commands. Demoting it removes the only defense against an agent (or a compromised/careless session) running `git push --no-verify origin main`.
2. **`core.hooksPath` is a per-clone git config that is NOT installed on managed-project clones, by deliberate design.** #1087's own security review found that auto-installing `core.hooksPath` against an arbitrary just-cloned third-party repo hands that repo's own tracked scripts execution with no operator confirmation — HIGH severity, removed before merge. That half of #1086 is intentionally deferred to #1088 ("do nothing" is a legitimate outcome there). Concretely, **today, and for as long as #1088 is unresolved, every managed-project workspace clone has zero git-native hook coverage** — `.githooks/pre-push` and `.githooks/pre-commit` never fire there, because `core.hooksPath` was never pointed at them. `block-main-push.sh`, by contrast, is wired process-wide: it resolves the ops fork from the session (pin-first, walk-up fallback) and fires on every `Bash` tool call regardless of which repo the command's cwd targets — see `.claude/settings.json`'s `block-main-push.sh` matcher, which walks up from `$PWD` (or the session pin) rather than assuming the ops fork's own working tree. Demoting it to advisory would leave every managed-project clone's agent-driven pushes and commits with **no blocking protection at all**, until/unless #1088 lands a different answer.

Neither gap is hypothetical or narrow — one is "any push/commit that adds one flag", the other is "the default state of every managed-project clone in the portfolio model this whole framework is built around." [AgDR-0104](AgDR-0104-trust-chain-controls-vs-backstops.md) is the framing this record has to reconcile with: it said a trust-chain hook should be labelled "THE control" or "a backstop to a server-side gate — then say so, and stop calling it enforcement." Read superficially, "backstop → stop calling it enforcement" sounds like "backstop → advisory." It is not, and the reason it is not is what AgDR-0104 was actually leaning on: in the case that record was written for (`block-unreviewed-merge.sh` vs. the forge's own branch protection), a **strictly more authoritative control already exists** — the forge's server-side gate sees structured state no local hook can spoof, so narrowing local trust and leaning on the forge loses nothing. Here, there is no equivalent stronger control to lean on: server-side branch protection was explicitly rejected for this exact ticket ("adopters install this framework onto arbitrary repos and forges... cannot be assumed to exist"), and the git-native hooks — while genuinely stronger than text-parsing on the *which-ref* axis — are not universally live the way `block-main-push.sh` is. Demoting the backstop here doesn't relocate trust onto something stronger; it just removes it, for the two scenarios above.

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **A. Keep `block-main-push.sh` exactly as-is (do nothing)** | Zero effort, zero regression risk | Leaves the honest-naming problem unaddressed — it's still implicitly treated as "the" control even though #1090 made the git-native push layer objectively stronger on ref-resolution; leaves commit-time enforcement on the ONLY layer with catalogued text-parsing residuals (AgDR-0113's #1081/#1083/#1084/#1085), with no git-native commit-time control to fall back on; doesn't harden the shared lib before PR-2 migrates onto it |
| **B. Full demote to advisory (the issue's own recorded, unmerged proposal)** | Simplest mental model — "git-native hooks are the control, everything else is cosmetic"; mirrors #1090's push-side shape exactly | Net reduction in real protection for two live, non-hypothetical scenarios: `--no-verify` (structurally bypasses every git-native hook, never `block-main-push.sh`) and managed-project clones with `core.hooksPath` never installed (#1088, deliberately deferred). Demoting the one layer immune to both removes coverage that has no replacement, not a labeling nicety |
| **C. Narrow partial demote** — advisory only when `core.hooksPath` is confirmed installed for the target clone, blocking otherwise | Reduces redundant blocking where a stronger layer is confirmed live | Detecting "is `core.hooksPath` correctly installed for THIS clone" from inside a PreToolUse hook running in the agent's own process (not necessarily the same shell context as the eventual `git` invocation) is real added complexity with its own failure modes; even when correctly detected, the `--no-verify` gap applies regardless of `core.hooksPath` state, so this option still leaves that gap open whenever the flag is used. Complexity cost without proportionate benefit |
| **D. Relabel + keep blocking (CHOSEN)** — leave `block-main-push.sh`'s behaviour untouched in this PR; add the missing `.githooks/pre-commit` git-native control; harden `_lib-protected-branches.sh` fail-closed; document `block-main-push.sh` as a blocking backstop, not the primary control, in this PR's artifacts and in a follow-up PR's doc pass | Zero protection loss (nothing that blocks today stops blocking); adds real new coverage that didn't exist before (`.githooks/pre-commit`); the two MEDIUM lib gaps close *before* a follow-up PR migrates `block-main-push.sh` onto the same lib, instead of being fixed under that migration's time pressure; honest naming achieved without the coverage cost of B | `block-main-push.sh`'s own known parsing residuals (AgDR-0113) remain live for a while longer — acceptable because nothing about this decision makes them worse; they are pre-existing, catalogued, and net-neutral-or-better against `dev` at every point in that AgDR's history |

## Decision

Chosen: **D — relabel `block-main-push.sh` as a blocking backstop, and keep it blocking.** Concretely, in this PR (#1086 step 3, PR-1 of 2):

1. `.githooks/pre-commit` ships as a new, git-native, **blocking** (`exit 1`) commit-time control. It resolves the branch via `git symbolic-ref --short HEAD` — no command-text parsing, no `cd`-prefix detection, no heredoc-awareness needed, because there is no command text here to parse. This closes the exact gap the issue's second review round found: before this PR, `.githooks/` contained no commit-time hook at all.
2. `.claude/hooks/_lib-protected-branches.sh` gains `is_protected_branch()` — a single shared predicate both `.githooks/pre-push` and `.githooks/pre-commit` now call, replacing each hook's own ad hoc `grep -qE` + `command -v` guard. It fails CLOSED in both of the ways the issue's review flagged as MEDIUM: a regex-evaluation error (e.g. an unbalanced-paren entry in `.git.protected_branches[]`) is treated as a match (protected), not a silent non-match; an absent or renamed `protected_branch_regex` function after a successful `source` is treated as a match (protected) with a visible `WARN`, not a silent allow. `.githooks/pre-push` is updated to use this shared predicate in the same PR — its net external behaviour for all 11 existing test cases is unchanged (verified: the full existing pre-push suite stays green), but it now inherits the fail-closed fix instead of carrying a second, independently-buggy copy of the same gap.
3. `block-main-push.sh` itself is **not touched** in this PR — no behavioural change, no code change. It keeps blocking (`exit 2`) exactly as it does today. This PR documents, here and in its own PR description, that it is honestly a **blocking backstop**: not the primary/preferred control any more (the git-native hooks are, for the reasons #1090's review already established on the push side), but not advisory either, because — per the Context section above — there is no stronger control it can safely be replaced by for the `--no-verify` and uninstalled-`core.hooksPath` cases.
4. A follow-up PR (step 3, PR-2) migrates `block-main-push.sh` onto `_lib-protected-branches.sh` (removing its inline, duplicate protected-branch resolution — the duplicate the issue's review already flagged) and updates its own header comments to the honest "blocking backstop" language this record establishes. **PR-2 does not demote it.** The ordering constraint the issue's unmerged proposal stated — "`pre-commit` must land and be installed by default BEFORE `block-main-push.sh`'s commit half becomes advisory" — is moot under this decision: there is no planned demotion for that ordering constraint to protect.

## Consequences

- **Zero protection loss.** Every push/commit shape `block-main-push.sh` blocks today still blocks after this PR. Nothing in this PR removes a check; it only adds `.githooks/pre-commit` and hardens the shared lib.
- **A new commit-time git-native control exists where none did before.** `.githooks/pre-commit` covers every clone with `core.hooksPath` correctly installed (today: the ops fork, via `/setup`) with ground-truth, parsing-free branch resolution — including the worktree case, for free, by construction (a linked worktree's `pre-commit` hook runs with that worktree's own checked-out branch; there is no `cd`-prefix special-casing to get right or wrong).
- **`_lib-protected-branches.sh` is fail-closed before PR-2 needs it to be.** PR-2's migration of `block-main-push.sh` onto this lib inherits an already-hardened foundation instead of having to fix these two MEDIUMs under migration pressure.
- **#1081, #1083, #1084, #1085 (block-main-push.sh's / the shared parser's text-parsing residuals) stay OPEN after this PR.** They are not touched, because `block-main-push.sh` is not touched. They remain candidates to close as "superseded at the git layer" once PR-2 lands equivalent commit-side, ground-truth coverage — that determination belongs to PR-2, not this record.
- **This AgDR is the ordering/authority reference PR-2 cites.** PR-2's own description should link back here rather than to the issue's unmerged "commit gate moves to pre-commit, block-main-push.sh becomes advisory" comment, which this record supersedes.
- **Honest-naming, achieved without AgDR-0104's "backstop → advisory" leap.** This record explicitly narrows that leap's applicability: it holds where a strictly stronger control already exists to lean weight onto (AgDR-0104's original merge-gate case); it does not hold where the "backstop" is the only layer covering a real gap the stronger control doesn't reach.
