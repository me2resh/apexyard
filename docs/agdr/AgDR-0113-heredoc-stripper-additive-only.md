# Heredoc-body stripping is an additive-question tool, never a gate pre-filter

> In the context of fixing me2resh/apexyard#1066 (git-command validators matching prose inside heredoc bodies), facing a choice between three parsing strategies and, across five review rounds, findings that the fix itself introduced FIVE distinct bypasses/over-narrowings of increasing subtlety, I decided to (a) strip heredoc bodies only for the "which ref / is this exempt" refinement question, never for the "is there a real git command here at all" gating question, (b) make the stripper itself two-pass and anchor-validated so it only ever removes CONFIRMED heredoc bodies, (c) give `block-main-push.sh` an independent, heredoc-parsing-agnostic check that scans every push-shaped occurrence in the raw command and blocks if any names a protected branch, (d) evaluate `is_tag_push`'s exemption PER-OCCURRENCE rather than as any single whole-command verdict, after two successive whole-command attempts each over-narrowed differently, and (e) strip surrounding quote characters from every extracted ref — because (a) and (b) together stop a stripper bug from silencing a gate, but do not stop a decoy ref sitting in text the stripper correctly declines to touch from winning a first-match extraction, (c) alone does not stop that same decoy from replacing the local-HEAD fallback for a ref-less push, and no single whole-command boolean can correctly separate a genuine tag push, a decoy, and an ordinary push from each other when more than one occurrence is present. This AgDR states plainly what is and is not guaranteed by this design, states the SCOPE at which every claim holds (not merely that a test exists), holds itself to both rules, and records that the guarantee ultimately rests on caller discipline no test can enforce.

## Context

`validate-branch-name.sh` and `block-main-push.sh` both need to know, from a raw Bash tool-call string, whether a `git push` / `git commit` is really happening and (for push) which branch is the destination. The naive approach — grep the whole command string for `git push` / `git commit` and pull the first ref-shaped token after it — breaks when the command also contains a heredoc: this repo's own commit messages and PR/review bodies routinely *discuss* git behaviour in prose (`git push`, `--tags`, `<<EOF`, C++'s `<<` operator), and a heredoc body is exactly where that prose lives.

The ticket's own repro is the clean, deterministic case:

```bash
cat > /tmp/m.txt <<EOF
The previous commit claimed terminal `git push` still runs the checks because
bin/run-pre-push-checks.sh hardcodes them.
EOF
git commit -F /tmp/m.txt
git push upstream fix/GH-1031-untrack-project-config-json
```

The first "git push"-shaped text anywhere in the raw string is inside the heredoc body ("`git push` still runs the checks"), so a naive scanner extracts `still` as the branch name and blocks a correctly-named push. `block-main-push.sh`'s commit-check has the mirror bug: it treats the mere substring "git commit" anywhere in the command as evidence a commit is happening, so a heredoc that only *discusses* a commit falsely blocks on a protected branch even though nothing is being committed.

## Options considered

The ticket's investigation notes listed three directions:

| Option | Pros | Cons |
|--------|------|------|
| **A. Strip heredoc bodies (and quoted strings) before matching** | Directly targets the repro; keeps the existing worktree-safe text-scan capability (#194/#547) intact | Narrower fixes elsewhere (per-statement scanning) still need the same heredoc-awareness as a prerequisite, so this isn't really competing with B — see below |
| **B. Validate per-statement / only the command's last statement** | Sounds simpler | Doesn't remove the ambiguity, it relocates it — a per-statement scanner still has to recognise a heredoc BODY line isn't a statement at all before it can skip it. And "only the last statement" breaks the existing commit-then-push compound check (block-main-push.sh must block a commit on a protected branch even when a push follows it) |
| **C. Narrow the text scan to the worktree case it was built for** | Reduces the scan's blast radius | Doesn't fix the ticket's own repro, which isn't a worktree scenario at all — it's a plain, single-checkout commit+push. Narrowing *when* the scan runs doesn't stop it *misreading heredoc prose on the calls where it still has to run* |

**Chosen: Option A** — strip heredoc bodies, refined below. B and C were rejected for the reasons in the table; neither closes the ticket's actual repro, and B in particular has to solve the same sub-problem A does, just less directly.

## The bug in the first implementation, and the second decision it forced

The first version of Option A (me2resh/apexyard#1075, the PR this ticket produced) stripped heredoc bodies with a single-pass scanner — any line containing `<<` followed by a word-shaped token was treated as a heredoc start, and everything after it was dropped until a matching terminator line was found (or, if none was found, until the command ended). Both hooks then ran their **presence checks** (`grep -qE 'git push'` / `'git commit'` — the boolean "should this hook even look at this command" gate) against that stripped text.

A security review of that PR found this was a bypass, not just an incomplete fix. Verified by stubbing `git` on `PATH` and confirming the push genuinely executes, eight distinct shapes made the single-pass stripper eat the real command:

| Shape | Why the single-pass stripper ate the real command |
|-------|------------------------------------------------------|
| Unterminated heredoc (`cat <<EOF` with no closing `EOF` line) | No terminator ever found → old design dropped the remainder of the command, including a real `git push` on a later line |
| Backslash-escaped delimiter (`<<E\OF`) | The old regex parsed the terminator as `E` (stopping at the backslash); the real closing line `EOF` never matches `E`, so it's effectively unterminated |
| Multi-word quoted delimiter (`<<'E O F'`) | The old regex can't capture a delimiter containing spaces; it parsed a stray leading quote into the terminator, which then never matches |
| Dotted delimiter (`<<END.OF`) | The identifier regex stops at the `.`; the parsed terminator (`END`) never matches the real line (`END.OF`) |
| `<<EOF` inside a quoted string, no real heredoc at all (`echo "docs say use cat <<EOF here" && git push origin main`) | The old design had no concept of "what follows this delimiter word on the same line" — any word-shaped token after `<<` was accepted as a heredoc start regardless of context |
| Commit message merely mentioning `<<EOF` (two separate lines, no chaining) | Same root cause as above, applied across a line boundary |
| Two heredocs on one line (`cat <<A <<B`) | The old design only recognised the first `<<` on a line and had no anchor check, so it entered heredoc mode on the first candidate and then, encountering the second literal `<<` on a subsequent line by itself, entered a SECOND heredoc whose terminator (`X`) never appeared — eating the real push that followed |
| C++ `operator<<` / shift usage in a quoted commit message (`git commit -m "use a << b shift"`) | Same root cause as the quoted-string case above |

Both `validate-branch-name.sh:33` and `block-main-push.sh:87` ran their presence check against the stripped (over-eaten) text, so for all eight shapes the gate silently exited 0 and the real push ran unvalidated.

### The framing that fixes it: additive vs. subtractive

The security review's core insight, which this AgDR adopts as governance for the whole file (`_lib-strip-heredoc.sh`) and everything that sources it:

> `extract_push_ref` is an **additive extractor** — it tries to answer "what is the ref"; a bug yields a wrong answer, and the caller still has real content (the raw command, an independent local-state fallback) to check against. Failure is local and visible.
>
> `strip_heredoc_bodies` is a **subtractive pre-filter on gate input** — it decides what a caller is even ALLOWED to see. A bug here produces *no question being asked at all*, silently and fail-open across every consumer simultaneously.

Concentrating the first kind of function (a shared, well-tested `extract_push_ref`) buys safety — one bug fixed once benefits every caller. Concentrating the second kind turns one parser mistake into a bypass across every gate that trusts it, which is exactly what the table above demonstrates across two gates (with a third, `verify-commit-refs.sh`'s `resolve_commit_workdir()` from #1073, a natural future adopter of the same kind of raw-command-text parsing).

## The decoy-ref hijack — a second, narrower bug the first fix left open

Fixing the presence-check bypass (governance rule 2 below) does not fix everything wrong with using a first-match extractor. `strip_heredoc_bodies` is now deliberately conservative: it only strips a heredoc it can CONFIRM (anchored + terminated). For a heredoc it correctly DECLINES to touch — a backslash-escaped delimiter (`<<E\OF`), a dotted delimiter (`<<END.OF`), or no heredoc at all, just a quoted string — the body is, correctly, left completely visible. But "visible" cuts both ways: if that body happens to contain a plausible, NON-protected decoy ref, `extract_push_ref`'s first-match semantics return the decoy — a confident WRONG answer, not an empty one:

```bash
cat > /tmp/m.txt <<END.OF
see git push origin feature/GH-1-safe
END.OF
git push origin main
```

`extract_push_ref` returns `feature/GH-1-safe` (not protected) here. The fail-closed check from the first fix round (governance rule 3 below) only engages when heredoc-aware extraction returns EMPTY — it does not, and structurally cannot, catch a confident wrong answer. Meanwhile real bash terminates the heredoc at the line that actually equals `END.OF` and executes `git push origin main` for real. Same mechanism with `<<E\OF` (backslash-escaped delimiter) and with no heredoc syntax at all (`echo "see git push origin feature/GH-1-safe" && git push origin main`).

This is **pre-existing**, not a regression introduced by this PR — `dev`'s original, unfixed code exhibits the identical hijack on all three shapes, because it was never heredoc-aware to begin with. It is #1066's original "first match wins" bug, surviving precisely in the residual shapes the (now-correct) stripper is honest about being unable to confirm.

**Fix, deliberately independent of heredoc parsing**: `block-main-push.sh` now also scans the RAW command for EVERY push-shaped occurrence (`_extract_all_push_refs_core` in `_lib-extract-push-ref.sh`) and blocks immediately if ANY of them names a protected branch — before `is_tag_push` is even consulted, so a decoy `--tags` mention can't hide a real protected-branch push either. This does not touch the stripper, does not care whether a heredoc was confirmed or declined, and does not depend on getting heredoc-delimiter parsing right at all: a decoy sitting in text this parser can't confirm as a heredoc body is still just TEXT, and "does any push-shaped text in this command name a protected branch" is answerable without knowing anything about heredocs. Verified against all three decoy shapes plus a confirmed-heredoc control (`.claude/hooks/tests/test_heredoc_bypass_shapes.sh`, cases X1–X4), proven RED against the pre-fix code first.

This fix is scoped to `block-main-push.sh` only. `validate-branch-name.sh` shares the same `extract_push_ref` and is exposed to the identical first-match mechanism, but the consequence there is lower-severity (a non-conforming branch NAME might not get caught, versus a real push landing on a protected branch undetected) and is recorded as residue below rather than fixed in this round.

## Decision

Seven changes across five review rounds, each closing a distinct gap the others leave open. Point 6 below folds in the history of two REJECTED whole-command attempts that preceded its final per-occurrence form — both are kept in this record, not summarised away, because each was itself a genuine, verified over-narrowing, not a hypothetical:

1. **`_lib-strip-heredoc.sh` is split into its own file** (moved out of `_lib-extract-push-ref.sh`) and its stripper is rewritten to be two-pass and conservative. A heredoc is only ever stripped when BOTH:
   - **Anchored**: everything after the delimiter word, on the same line, is empty, a `#` comment, or a plain output redirection (`>`, `>>`, an fd redirect like `2>`, or `&>`) — nothing else. A `<<` inside a quoted string, an arithmetic expression, or followed by `&&`/`||`/`;`/a pipe/another `<<` is never treated as a heredoc start.
   - **Terminated**: scanning forward from the candidate start, some later line — after tab-stripping for `<<-` — exactly equals the delimiter. If no such line is found anywhere in the rest of the command, nothing is stripped; the text from that point on is returned completely unchanged.

   Re-verified against all eight shapes: with this stripper, **none of them are ever stripped at all** — the (fixed) stripper declines every one of them, leaving the text byte-for-byte identical to the raw command. The legitimate heredoc shapes (the ticket's own repro, `<<-EOF`, `<<'EOF'`, `<<"EOF"`, a trailing redirect like `cat <<EOF > file`) are still stripped correctly.

2. **The presence check — "is there a real git push/commit here at all" — always runs against the RAW, unfiltered command.** Never against this file's output, regardless of how conservative the stripper is believed to be. `strip_heredoc_bodies` (and `extract_push_ref` / `is_tag_push`, which call it internally) may only be used to refine an ADDITIVE question — "given that a real operation is independently known to exist, which ref / is it exempt" — never to decide whether the gate should fire.

   Concretely: `validate-branch-name.sh` and `block-main-push.sh`'s `grep -qE 'git push'` / `'git commit'` presence checks, and both hooks' `cd`-target extraction for worktree resolution, operate on the raw `$COMMAND` throughout. `is_tag_push` and `extract_push_ref` are still called with the raw command too (they strip internally) — this is safe for `extract_push_ref` specifically because of point 3 below; **it is NOT safe for `is_tag_push` on its own**, which is why point 5 exists.

3. **Fail closed on disagreement, for the push ref specifically.** `_extract_push_ref_core` (the token-parsing logic, now exposed directly, no stripping) is run a second time against the RAW command as a comparison signal. If the heredoc-aware `extract_push_ref` finds no ref, but the raw-text core parser finds something ref-shaped, that disagreement means a heredoc may be hiding the real destination rather than this genuinely being a ref-less push — falling back to local-HEAD validation in that case could validate the wrong branch. Both hooks now BLOCK instead, with a message pointing at the ticket's own mitigation (split the heredoc-writing and the git command into separate Bash calls).

   **The sharper framing for why this specific check works, and where it stops working (supplied during code review, and better than this AgDR's earlier "additive vs subtractive" wording for this specific case):** a *missing* answer is additive-safe — the fail-closed check above exists precisely to catch it. A *wrong, non-empty* answer is different in kind: it is **substitutive, with no backstop**. In `block-main-push.sh`, a non-empty `PUSH_DST` *replaces* the local-state fallback outright — nothing downstream double-checks a non-empty value, so a confidently wrong ref decides which branch gets checked, full stop. This is exactly what makes the decoy-ref hijack (below) dangerous: for the shapes where the (fixed) stripper declines to strip, both the heredoc-aware parser and the raw-text parser **agree** on the same wrong, non-empty ref — there is no disagreement for point 3's check to catch, because the fail-closed comparison only fires on disagreement, and agreement-on-a-wrong-answer produces none.

   An earlier version of this AgDR claimed `is_tag_push` "does not need the equivalent treatment: stripping can only ever *remove* text, never manufacture a `--tags` mention that wasn't in the raw command, so the only failure direction is a false NEGATIVE." **That claim is false, and was verified false at the hook level, not just in theory.** The reasoning about stripping was correct as far as it went — stripping alone cannot invent a `--tags` mention — but it missed that for an UNCONFIRMED heredoc, stripping does not happen AT ALL (it correctly declines), so decoy prose that was already sitting in the raw command survives untouched and can match `is_tag_push`'s pattern directly. That is a genuine, verified false POSITIVE, not a false negative:

   ```bash
   cat > /tmp/m.txt <<END.OF
   we always use git push --tags for releases
   END.OF
   git commit -m "bad commit"
   ```

   `is_tag_push` returns TRUE here (the decoy line matches `\bgit\s+push\b.*\s--tags(\s|$)`), even though there is no real tag push anywhere in the command. Before this round, `block-main-push.sh` treated that TRUE as a script-level `exit 0` — which didn't just skip the push-branch-check (arguably fine, since it has no ref to protect here anyway), it skipped the **entirely unrelated commit-check section further down the same script**, letting a real `git commit` on a protected branch (`dev`) slip through with zero inspection. Verified: `rc=0` before the fix in this round, `rc=2` after.

4. **`block-main-push.sh` scans every push-shaped occurrence in the raw command, independent of heredoc parsing entirely, and blocks if any names a protected branch.** This is the fix for the decoy-ref hijack above. It is deliberately NOT built on top of `strip_heredoc_bodies` or `extract_push_ref` — it does not ask "is this a heredoc", "is it confirmed", or "which one is the real command"; it asks only "does any push-shaped piece of text in this raw command name a protected branch", which is answerable regardless of how good or bad heredoc-delimiter parsing is. This is what makes it a genuine backstop for point 3 rather than a variation on the same mechanism: point 3's fail-closed check can only fire when heredoc-aware extraction returns *empty* and disagrees with the raw parse; a decoy ref is precisely the case where both parsers agree on something else — confidently, wrongly, non-empty, with no disagreement to catch. **Test:** `test_heredoc_bypass_shapes.sh` cases `X1`–`X4` (X1–X3 are the decoy shapes, proven RED against the pre-fix code first; X4 is the confirmed-heredoc control).

5. **`is_tag_push`'s verdict in `block-main-push.sh` no longer causes a script-level exit.** A `true` result now only sets a flag; it never short-circuits the whole script, so the commit-check section always still runs regardless of what `is_tag_push` decided. **This closes a real, verified bug, not a hypothetical one**: before this point, `is_tag_push`'s `true` was a bare `exit 0`, and decoy prose carrying tag evidence (`--tags`, `tag <name>`, `refs/tags/`) inside a heredoc `strip_heredoc_bodies` correctly declines to strip could trigger it with no real tag push anywhere in the command — silently skipping the ENTIRELY UNRELATED commit-check section further down the same script and letting a real `git commit` on a protected branch through uninspected. **Test:** `test_heredoc_bypass_shapes.sh` case `TAGDECOY` (proven RED first: `rc=0` before this point's fix, `rc=2` after).

   An earlier draft of this point additionally claimed that skipping the push-branch-check here "costs nothing" because decision point 4's scan-all "already covered it independently." **That claim was false and is corrected by point 6 below — it does not merely soften to residue, because a real gap it described as safe was still open when it was written.** Scan-all (point 4) only ever sees EXPLICIT refs; it has nothing to say about a bare, ref-less `git push`, and the local-HEAD fallback that WOULD catch a ref-less push on a protected branch lives entirely inside the block this flag skips. Trusting an unattributed `is_tag_push` verdict to skip that block was, for that one shape, an actual **under-block** — the failure direction was the dangerous one, not the safe one, until point 6 closed it.

6. **`is_tag_push`'s verdict is evaluated PER-OCCURRENCE, never as a single whole-command boolean — `_command_has_untagged_refless_push` in `_lib-extract-push-ref.sh`.** This point exists because TWO successive whole-command verdicts, tried in sequence, each failed a DIFFERENT genuine shape:

   - **The coupling that made this dangerous, not just incomplete:** a `--tags`/`tag <name>`/`refs/tags/` match can sit in decoy text ALONGSIDE a real, separate, ref-less `git push` elsewhere in the same command (`cat > /tmp/m.txt <<END.OF\nwe always use git push origin --tags for releases\nEND.OF\ngit push`), or the tag-evidence match can be entirely DETACHED from any push segment at all (`echo "see refs/tags/v1 docs" && git push` — the evidence and the real push aren't even in the same clause). Either way, `is_tag_push`'s global checks return `true` for a command whose one real push carries no tag evidence of its own.
   - **Why "just don't skip" (point 5 alone) wasn't enough:** even after point 5 stopped trusting `is_tag_push` to skip the whole block, the ordinary `extract_push_ref` call inside that block still read the SAME decoy segment and returned a confident, non-empty, non-protected-*looking* ref (e.g. `"for"` from `git push origin --tags for releases`) — which silently REPLACED the local-HEAD fallback exactly as the point-3 framing above describes ("a non-empty answer is substitutive, with no backstop"). Verified: the security reviewer's own minimal pair — `git push` alone on `main` blocks (`rc=2`); the same bare push with the decoy heredoc added returned `rc=0` — even with point 5 already applied.
   - **First attempted fix, and why it was wrong:** require the command to contain EXACTLY ONE push-shaped occurrence in total, and that occurrence carries the tag evidence. This over-blocked a normal release step — pushing tags to two remotes in one command (`git push origin --tags && git push upstream --tags`) has TWO occurrences, both genuinely tag-shaped, no decoy anywhere — rejected anyway, because "exactly one" counts occurrences instead of asking whether each is safe. **Test:** `test_heredoc_bypass_shapes.sh` case `N7`, proven RED under the exactly-one rule, GREEN after the per-occurrence fix below.
   - **Second attempted fix (same review round), and why it was ALSO wrong:** stop counting occurrences and instead require EVERY occurrence to carry its own tag evidence. This repaired `N7`, but a subsequent review round found it broke a THIRD genuine shape neither prior version had been tested against: an ordinary push to a non-protected branch, followed by a separate, genuine tag push, no heredoc anywhere at all (`git push origin feature/GH-1-x && git push origin --tags`). Under "every occurrence must carry evidence," the ordinary push's total lack of tag evidence untrusted the WHOLE command, forcing `PUSH_DST` empty and triggering the fail-closed block — with a message blaming heredoc structure that does not exist anywhere in this command. `dev` allows this command; so did this file before either whole-command version existed. **Test:** `test_heredoc_bypass_shapes.sh` case `MIXED`, proven RED under the every-occurrence rule, GREEN after the per-occurrence fix below.
   - **What both attempts got wrong, structurally:** an occurrence that carries an EXPLICIT ref needs no special handling from this function at all — decision point 4's scan-all has ALREADY checked it against the protected list, independent of whether it's a tag push. Folding that occurrence into a whole-command "does the tag-push signal deserve trust" verdict was always the wrong question, in both directions (rejecting it alongside a genuine decoy in the first attempt's "exactly one," and rejecting it alongside a genuine tag push in the second attempt's "every occurrence").

   **The fix: ask the question per-occurrence.** For each push-shaped occurrence: if it carries its own tag evidence, it is exempt. If it carries an explicit ref, decision point 4's scan-all has already checked it. Only an occurrence with NEITHER — a bare, ref-less push with no tag evidence of its own — is unaddressed by anything else in the hook, because scan-all has no ref to check and the tag exemption doesn't apply. `_command_has_untagged_refless_push` returns true exactly when such an occurrence exists anywhere in the command. When it does, `PUSH_DST` is forced to empty (bypassing whatever `extract_push_ref` would have read from a DIFFERENT occurrence's decoy or tag-evidence text) so the command falls into either the point-3 fail-closed block or the local-HEAD fallback — never into "validate a different occurrence's ref and pass." When no such occurrence exists, the push-branch-check is skipped entirely: every occurrence is either exempt or already checked. **Test:** `test_heredoc_bypass_shapes.sh` cases `TAGBOUND control`, `TAGBOUND T1`, `TAGBOUND U4` (bare/ref-less decoy shapes, must block), `TAGBOUND T4 control`, `TAGBOUND T5 control` (genuine tag pushes, must stay exempt), `N7` (two-remote release step, must stay exempt), and `MIXED` (ordinary push + separate tag push, must stay allowed) — all eight proven RED against at least one of the two rejected whole-command versions first, GREEN against the per-occurrence fix.

7. **`_extract_push_ref_core` and `_extract_all_push_refs_core` strip a single pair of surrounding quote characters from the extracted ref.** `git push origin "main"` (or `'main'`) previously extracted the token WITH its quotes attached, which never matches `^(main|master|dev|develop)$`, so the push to a protected branch executed unvalidated — no heredoc, no decoy, a plain quoting gap in the token extraction itself, filed and tracked as me2resh/apexyard#1079 and closed by this fix. Mirrors `block-main-push.sh`'s existing `cd`-target quote-stripping, which the #580 review of #549 called "the security-critical part" of that fix for the identical reason: an unstripped quote character defeats an exact-match regex silently. **Test:** `test_heredoc_bypass_shapes.sh` cases `QUOTED-REF` (both quote styles, proven RED against the pre-fix code first, plus a regression control confirming an unquoted, non-protected branch still passes).

## Consequences — what is guaranteed, what is not, stated plainly

An earlier draft of this section said the documented residue has "no safety impact — only a minor UX one." **That was false, and it is exactly the sentence a future adopter would lean on.** A later draft additionally claimed a specific skip "costs nothing" — also false. A still later draft's fix for THAT claim over-narrowed and false-blocked a normal two-remote release step (`N7`) — caught in the next review round. The very next attempt to fix `N7` over-narrowed AGAIN, in the opposite direction, false-blocking an ordinary push alongside a separate genuine tag push (`MIXED`) — caught by a second reviewer converging independently on the same document. Four reasoned claims of coverage or correctness in a row, written without a test pinning them, each caught in a subsequent round by a different reader. That recurring shape is why this AgDR states, and applies, two rules for its own future edits (see the governance section below) — every remaining claim below either cites the specific test case that proves it, or is written as residue, and where a claim only holds at a particular scope, it says so.

**What genuinely holds — cited to the test that proves it, scope stated explicitly where the test doesn't exercise the fully general case:**

- Presence checks (`grep -qE 'git push'` / `'git commit'` — the "should this hook look at this command at all" gate) never consult this file's stripped output, in either hook. That single rule is what stops a stripper bug (over-eating, under-eating, any future parsing mistake) from making a gate skip itself silently. **Test:** all eight of `test_heredoc_bypass_shapes.sh`'s `A`–`H` cases, proven RED against the single-pass stripper first. **Scope:** holds regardless of whether the real push has an explicit ref or is bare — this claim is genuinely general, because it's about whether the check runs at all, not about what it finds.
- The ticket's original, deterministic repro is fixed: a heredoc-authored commit message that merely discusses `git push` no longer causes the wrong branch to be validated. **Test:** `test_heredoc_bypass_shapes.sh` case `X4`; `test_extract_push_ref_heredoc.sh`'s ticket-repro case. **Scope:** the real push in this case has an explicit ref.
- `block-main-push.sh` scans every push-shaped occurrence in the raw command and blocks if any names a protected branch, independent of whether heredoc-delimiter parsing succeeds. **Test:** cases `X1`–`X3`. **Scope — read this before citing this claim elsewhere: this holds ONLY when the real push carries an EXPLICIT ref.** All three cited cases end in `&& git push origin main` — an explicit ref is exactly what this mechanism inspects; it has nothing to check for a bare, ref-less push (see the residue entry below, and decision point 6, for the mechanism that covers that different case).
- `is_tag_push`'s verdict in `block-main-push.sh` can no longer suppress the commit-check section. **Test:** case `TAGDECOY`. **Scope:** general — this is about a script-level `exit` never firing on `is_tag_push` alone, independent of what any occurrence contains.
- `is_tag_push`'s exemption is evaluated per-occurrence and forces the ref-less fallback path (never a hijacked decoy ref) whenever any occurrence is both untagged and ref-less. **Test:** cases `TAGBOUND control`, `TAGBOUND T1`, `TAGBOUND U4` (bare decoys, must block), `TAGBOUND T4 control`, `TAGBOUND T5 control` (genuine single tag pushes, must stay exempt), `N7` (genuine multi-remote tag push, must stay exempt), `MIXED` (ordinary explicit-ref push alongside a genuine tag push, must stay allowed). **Scope:** this is the one claim in this list that IS fully general by construction — it's stated per-occurrence specifically because no whole-command scope restriction proved safe (see decision point 6's history of two rejected attempts).
- `git push origin "main"` and `git push origin 'main'` are validated as `main`, not as the literal quoted token. **Test:** cases `QUOTED-REF` (both quote styles) plus a regression control. **Scope:** general — the strip applies to every extracted ref, in both extraction functions, regardless of heredoc, decoy, or tag-evidence state.

**What does NOT hold — residue, stated without softening, each either verified or explicitly marked as reasoning rather than a pinned test, and each scoped so it isn't confused with an adjacent claim that DOES hold:**

- **For shapes the parser declines to strip (unconfirmed heredocs), a decoy ref in the unstripped body can still win a first-match extraction. This affects BOTH hooks — it is NOT closed for `block-main-push.sh`.**

  **Correction (round 8, verified twice).** An earlier version of this bullet claimed decision point 4 closed this for `block-main-push.sh`, citing cases `X1`–`X3`. That claim is **false**, and the citation is why it survived three audits: all three cited cases end in `&& git push origin main`, an *explicit* ref, so they hold that dimension constant while the sentence asserted the general case. Point 4's scan-all only ever sees explicit refs; a **ref-less** push has none. Measured on a sandbox checked out on `main`: a bare `git push` blocks (rc=2), and the same bare push behind a `<<END.OF` decoy heredoc is **allowed** (rc=0). Pre-existing on `dev`, not introduced here.

  Tracked as me2resh/apexyard#1084, which records that `_command_has_untagged_refless_push` already detects this shape and is merely gated behind `if is_tag_push` — a one-line hoist closes it without reintroducing the over-narrowing that point 6 fixed.

- **A genuine tag push prefixed to a bare `git push origin HEAD` bypasses the protected-branch check — verified, and NOT the same defect as #1084.** Measured on a repo checked out on `main`, with a stubbed `git` so the push genuinely executes:

  ```bash
  git push origin HEAD                              # rc=2, blocked (control)
  git push origin --tags && git push origin HEAD    # rc=0, ALLOWED
  ```

  **Net-neutral against `dev`** across history — `dev`=0, `bc45eea`=2, this HEAD=0. Point 6's "exactly one occurrence" rule closed it incidentally, and the per-occurrence redesign that replaced it (necessary, since that rule false-blocked legitimate two-remote tag pushes) reopened it. Merging introduces no bypass not already on `dev`.

  **Scope, and why it is filed separately from #1084:** in #1084's shape `is_tag_push` is *false*, so `_command_has_untagged_refless_push` is never called and the fix is to hoist it. Here `is_tag_push` is *true*, the predicate **is** called, and it *misclassifies* — its token walk returns non-empty `HEAD` while `_extract_all_push_refs_core` deliberately treats `HEAD` as no-ref (`[ "$ref" = "HEAD" ] && continue`). **Applying #1084's hoist does not close this**, and closing #1084 could reasonably be read as handling the class. Tracked as me2resh/apexyard#1085.

  Not pinned by a test: the bypass suite has no `HEAD`-plus-tag-occurrence case, which is why it ran 36/36 with this live. It does **not** close it for `validate-branch-name.sh`, which shares `extract_push_ref`'s first-match semantics and has no scan-all backstop — a non-conforming branch NAME hidden behind a conforming-looking decoy can still slip past the naming gate. **Not pinned by a test in this repo** — reasoning only, carried over from the ref-hijack analysis; tracked as me2resh/apexyard#1081 rather than left as prose alone.
- **`is_tag_push`'s decoy-prose exposure is fixed for `block-main-push.sh` only — not for `validate-branch-name.sh`, which has no equivalent second section to protect.** The reasoning for deferring this, more precise than "lower severity": what made the `block-main-push.sh` bug dangerous was a *coupling* — a push-shaped boolean (`is_tag_push`) governing an UNRELATED section (the commit-check). `validate-branch-name.sh` has no second section; an early exit there skips only what the boolean is actually about (push-branch validation), which is the SAME severity class as the pre-existing ref-hijack residue above, not a novel bug this PR introduced. The bug class that justifies point 5/6's fix — one gate's boolean silently disabling a DIFFERENT gate's check — does not exist there. **Not pinned by a test in this repo** — filed as me2resh/apexyard#1081 instead of left as prose-only residue.
- **A new, deliberately-accepted false-block was introduced, in the safe direction, as a side effect of the point-4 fix.** `block-main-push.sh`'s scan-all check operates on the RAW command, so a legitimate, well-formed heredoc that merely *discusses* pushing to a protected branch in prose — with no real push to it anywhere in the command — can now cause an otherwise-benign push to a different branch to be blocked. **Not currently pinned by a test**; recorded rather than chased, per the standing reasoning in this document: occasional over-blocking on prose is the tolerated failure, a silent bypass is not.
- **A second, distinct false-block, on `validate-branch-name.sh`, caused by the fail-closed check itself (decision point 3) — verified, not reasoning:**

  ```bash
  cat > /tmp/m.txt <<EOF
  Remember: we should git push origin feature/GH-1-ok when ready.
  EOF
  git commit -F /tmp/m.txt
  ```

  There is no real `git push` anywhere in this command — just a commit, whose message happens to discuss one, inside a CONFIRMED (correctly-stripped) heredoc. `dev`'s original code returns `rc=0` (verified against `/tmp/orig_validate-branch-name.sh`): it extracts the SAME decoy ref (`feature/GH-1-ok`) from the raw text every time, and that decoy happens to be conforming-shaped, so it validates clean and passes. The current code returns `rc=2` (verified): heredoc-aware extraction correctly finds no push, the fail-closed check compares against the raw parse, finds the same decoy, and blocks — because that check triggers on any non-empty disagreement, not on whether the disagreeing value looks well-formed. Good error message, safe direction, but it is a sub-case of what #1066 set out to fix: the promise holds when a real push follows the heredoc, not when none does at all. **Not currently added as a repo test** — verified by hand against both code versions during review; worth a regression test if this file is touched again.
- **A genuinely ref-less push, sitting alongside heredoc prose that itself contains a ref-shaped push mention, now blocks where `dev` fell back to local HEAD.** A bare `git push` (relying on upstream tracking) in the same command as a heredoc discussing `git push origin some-branch`: the heredoc-aware parser correctly finds no ref for the real push, the raw-text comparison (decision point 3) finds the decoy's ref-shaped text and disagrees, and the fail-closed block fires instead of falling through to `dev`'s local-HEAD check. Safe direction (over-blocking), not chased. **Not currently pinned by a test in this repo** — reasoning only.
- **N1 — a genuine tag push after a heredoc whose prose merely mentions ANY push, with no decoy ref or tag evidence in it, now blocks where it previously would have passed — verified, not reasoning:**

  ```bash
  cat > /tmp/m.txt <<EOF
  Remember to git push carefully.
  EOF
  git push origin --tags
  ```

  This is a CONFIRMED, correctly-stripped heredoc — `strip_heredoc_bodies` removes the body cleanly, and there is no decoy ref or tag-evidence anywhere. But decision point 4's scan-all and decision point 6's per-occurrence check both operate on the RAW command, so the heredoc's own prose line ("Remember to git push carefully.") is itself seen as a push-shaped occurrence — bare (no second token forms a ref) and evidence-less (no `--tags`/`tag <name>`/`refs/tags/`). `_command_has_untagged_refless_push` correctly identifies it as exactly the untagged-ref-less shape point 6 exists to force a fallback for, and the local-branch check then fires on the current branch (`main`), blocking a push that has nothing wrong with it. Verified: `rc=2` on `main`. **This is the same prose-over-block trade already accepted for decision point 4 above** ("a legitimate heredoc that merely discusses pushing... can now cause an otherwise-benign push... to be blocked") — it is not a new category of risk, but it was undocumented for the per-occurrence check specifically, and it should not have been. **Not currently pinned by a test in this repo** — verified by hand during review.
- **The anchor+two-pass stripper recognises a handful of exotic heredoc-delimiter shapes as heredoc-*like* but never actually strips them**, because the real terminator can't be confidently computed or confirmed: backslash-escaped, multi-word-quoted, or dotted delimiters (`<<E\OF`, `<<'E O F'`, `<<END.OF`); two heredocs on one line (`cmd <<A <<B`); a here-string (`<<<`) combined with a heredoc on the same line. **Test (the declining-to-strip behaviour itself):** cases `B`, `C`, `D`, `G` all pass through the (fixed) stripper unchanged and are handled instead by the RAW-text mechanisms in points 2 and 4. This has no impact on the presence-check guarantee (which never depends on stripping succeeding), but it is precisely where a decoy can still survive to be first-matched — it is the boundary of what decision points 4 and 6 cover for the one hook they were applied to.
- **The redirect/pipe truncation hole is PRE-EXISTING, shared by every extractor in this file (including the "heredoc-independent" ones), and is NOT closed by any decision point above — left alone by explicit instruction.** `_extract_push_ref_core` (and therefore `extract_push_ref`, `_extract_all_push_refs_core`, and `_command_has_untagged_refless_push`, all of which build on the same redirect-stripping) truncates a line at its FIRST `>` or `|`, even when that redirect appears BEFORE a real `git push` on the same line rather than after it: `echo x > /tmp/f && git push origin main` and `echo x | cat && git push origin main` both return NO refs from every extraction function in this file — verified against both the current code and `dev`'s original, unfixed `_lib-extract-push-ref.sh`, so this is not a regression introduced by any round of this PR. The consequence is real: when the redirect-truncated command's local branch is not the protected one it's pushing to, the push goes through with `rc=0` (verified, `test_heredoc_bypass_shapes.sh` does not currently cover this). This matters specifically because decision point 4 was described above as "heredoc-independent" and "answerable regardless of how good or bad heredoc-delimiter parsing is" — true, but it is not independent of THIS hole, since it shares the same underlying segmentation. **Out of scope for this round by explicit instruction; not currently pinned by a test in this repo.** **Tracked as me2resh/apexyard#1083.**

**This safety rests on caller discipline, which no test can enforce.** Every guarantee above depends on every future caller of `strip_heredoc_bodies` / `extract_push_ref` / `is_tag_push` respecting the governance rule in `_lib-strip-heredoc.sh` — using them only for additive refinement, never as a gate's own presence pre-filter. A test suite can (and does, here) prove the CURRENT two call sites respect that rule. It cannot prove a future call site will. That is a property of code review and this document, not of `test_heredoc_bypass_shapes.sh`.

**The two rules this AgDR now holds itself to, going forward.**

Five rounds of review on this single ticket found five separate claims of coverage or correctness the code did not actually provide — each narrower and more defensible than the last: an over-broad "no safety impact," then a "costs nothing" for one specific skip, then an "exactly one occurrence" rule that false-blocked a genuine two-remote release step, then an "every occurrence must carry evidence" rule (the very next attempt to fix the previous one) that false-blocked a different genuine ordinary-push-plus-tag-push compound. The recurring shape was always the same: a reasoned guarantee written into this document without a test pinning it. The first rule adopted to fix this, after the fourth claim:

> **Every "X is covered by Y" sentence in this AgDR (or any future security AgDR) must either cite the specific test that proves it, or be written as residue.**

That rule caught real problems and is still necessary — but it was not sufficient. The fifth false claim (**"Decision point 4 closes this for `block-main-push.sh` (verified: cases X1–X3)"**, stated as a general claim about `block-main-push.sh`) had an honest, RED-proven citation, and still slipped past the citation rule, because `X1`–`X3` all end in `&& git push origin main` — an explicit ref. The citation was real; it just didn't reach as far as the sentence claimed. Citation discipline confirms a test *exists*; it does not confirm the test exercises the claim *at the scope the claim is written at*. That gap is closed by a second rule:

> **A coverage claim must state the scope at which it holds, the cited test must exercise it at that scope, and where the cited tests hold a dimension constant — explicit-ref vs. ref-less, protected vs. not, confirmed vs. unconfirmed heredoc — the claim inherits that constraint and must say so.**

This document has been re-audited against BOTH rules as of this revision — every claim in the "what genuinely holds" list above either names a test case with its scope stated, or is explicitly marked as unpinned reasoning in the residue list. Any future edit to this document that adds a coverage claim must do the same, and must specifically ask: *is there a dimension my cited tests hold constant that my sentence doesn't mention?*

**Adopter condition for `verify-commit-refs.sh`'s `resolve_commit_workdir()` (#1073, queued).** `_lib-strip-heredoc.sh` was split into its own file specifically so this hook can adopt it. But `resolve_commit_workdir()` is not a drop-in case of "extract a ref, fall back if empty" — it resolves a *path*, which a gate then reads a branch FROM. The same bug class transplants directly: if stripping over-strips and the function's result comes back empty (or, by the decoy-ref analogy, a confident wrong path), the caller must **fail closed**, not silently fall back to the hook's own session cwd — falling back to session cwd in a worktree session is the exact false-negative shape #549/#727 exist to prevent, and falling back to session cwd on an AMBIGUOUS heredoc-affected result reintroduces a bypass in a new hook rather than closing one. Any PR adopting this helper must show the equivalent of decision points 2–3 (raw presence check, fail-closed on disagreement) for its own empty/ambiguous case before merging.

**Why sharing the helper is judged safe despite all of the above.** The security review that found the first-round bypass considered, and initially rejected, sharing `_lib-strip-heredoc.sh` across hooks — a shared subtractive filter with a bug is a bug shared by every consumer at once. That objection is withdrawn here because the coupling it worried about was removed *architecturally*, not patched over: after decision point 2, this file's stripped output can no longer reach a presence check in either existing consumer, by construction, not by convention alone backed by a comment. A future bug in the stripper therefore costs ref *precision* (an additive question, with a fallback) in whichever hook has one, never gate *existence* (a subtractive question, with no fallback) — provided the adopter condition above is honoured. That distinction, not the mere fact that the code is now reusable, is what makes sharing this file across hooks defensible.
