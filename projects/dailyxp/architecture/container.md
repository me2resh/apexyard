## How to use this template

1. This file lives at `projects/dailyxp/architecture/container.md` (portfolio docs). The in-repo mirror, if you want one, is `docs/architecture/container.md`.
2. Replace placeholders with real containers as `da5ater/dailyxp-api` lands. A "container" is a **deployable / runnable unit**, not a Docker container.
3. Keep it to 5–9 containers — today's diagram is ~6 including the future hosted boundary.

## What goes in L2 (container)

- Every deployable unit that exists today (plugin host trio + local envelope) plus the planned Rails boundary (drawn dashed by intent — remove the box until the repo exists if you prefer strict as-is).
- External systems the containers actually talk to (`/etc/localtime` symlink, Marketplace, GitHub).
- Arrows with direction + protocol (`Qt signals`, `omarchy-shell verbs`, `Filesystem`, `HTTPS`).

## What does NOT go in L2

- Classes inside `EventModel.js` / `PlanningModel.js` — that's L3.
- Deployment topology (EC2 vs home server, regions, AZs) — deferred to vision.md + issue #13.
- Every side service (logging, metrics) — the plugin has no hosted observability yet; note it in vision.md.

## Relation to the L1 context diagram

Collapse `bar_widget + panel + state_service + local_state + event_model` back into the single `System(DailyXP)` box from `context.md`. External relationships (Omarchy Marketplace, GitHub, Rails API) should still match at L1.

## Maintenance

More volatile than L1. Update when:

- `da5ater/dailyxp-api` is created (split or merge the hosted boundary)
- A new container appears (mobile client, second plugin kind, worker)
- The sync protocol changes the `local_state → rails_api` hop
- The Day Boundary or timezone source changes the `state_service → localtime` hop

Expect to revisit every few releases. If it churns every sprint, the architecture is churning faster than it should be.
